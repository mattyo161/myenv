# 0002 — How travel-mode gets root, runs in the background, and is configured

**Status:** Accepted · **Date:** 2026-07-05 · **Area:** `scripts/travel-mode`, `roles/extras`

## Context

travel-mode keeps a laptop awake (lid closed, on battery) and auto-recovers
internet while working off a hotspot. One of its three mechanisms —
`pmset -a disablesleep` — changes a system-wide power setting and requires
root. The predecessor (`car-mode` shell functions in `~/.zshrc.local`) called
plain `sudo`, which works in a terminal but not for an unattended background
service; its background variant was an unsupervised forked loop tracked by a
pidfile, and its config (SSID list) lived as shell variables in a machine-local
rc file.

Promoting it into the repo forced three decisions: how to get root unattended,
how to run in the background, and where configuration lives.

## Decision

1. **Root via a scoped sudoers drop-in, not a root daemon.**
   `/etc/sudoers.d/travel-mode` grants the user NOPASSWD for exactly two fixed
   command lines — `/usr/bin/pmset -a disablesleep 1` and `... 0` — with no
   wildcards, installed by ansible with `validate: visudo -cf %s`. The script
   always runs unprivileged and calls `sudo -n` for just that toggle.

   *Rejected — root LaunchDaemon:* would get privileges implicitly but runs the
   entire ping/`networksetup` monitor loop as root for no benefit; a much
   larger audit surface than one whitelisted command.

   *Rejected — dedicated service user:* on macOS, `pmset` still needs root, so
   a separate user ends up needing the same sudoers grant — extra moving parts,
   same trust boundary.

   *Rejected — caffeinate-only (no root anywhere):* loses the defining feature;
   closing the lid on battery sleeps the machine.

2. **Background mode is a per-user launchd LaunchAgent, not a pidfile fork.**
   `travel-mode start` writes `~/Library/LaunchAgents/local.travel-mode.plist`
   (`KeepAlive` true) and `launchctl bootstrap`s it; `stop` boots it out and
   removes the plist. launchd supervises the worker — it survives closing the
   terminal and restarts on crash, which a pidfile-tracked `&` loop cannot do.
   The plist is generated by the script rather than templated by ansible so the
   tool stays a single portable file and ansible's job stays declarative
   (symlink + sudoers + config seed).

3. **Configuration is a machine-local file, not group_vars.**
   `~/.config/travel-mode/config` is a shell fragment sourced by the script.
   SSID lists are per-machine and mildly private, so they stay out of the
   shared repo; editing the list must not require an ansible run (you're often
   configuring it in a parking lot). Ansible seeds a commented default with
   `force: false` so user edits are never clobbered. WiFi passwords are never
   stored — reconnect uses SSIDs already saved in the Keychain.

## Consequences

- `travel-mode start`/`stop` work unattended once the extra is applied; without
  it, foreground `run` still works via an interactive sudo prompt.
- The sudoers grant is trivially auditable and removable (delete one file).
- If the script's own path changes (it's symlinked from
  `/usr/local/bin/travel-mode` into the repo), a loaded LaunchAgent keeps the
  old path until the next `stop`/`start` cycle, since the plist embeds the
  resolved script path at `start` time.
- `pmset disablesleep` persists until reverted; both `stop` and the foreground
  exit trap restore it, but a hard crash of the whole machine mid-travel-mode
  leaves it set until the next `travel-mode stop` (visible in
  `travel-mode status`).
